# 协议 v3 全量复测（2026-10-22）

这一轮用的是**换过卷的协议**：`SCHEMA_VERSION` 2 → 3，Gold 补了工具入参、禁止调用、逐轮答复三类断言，报告加了 `contract` 维度。数字与同一天的 v2 轮次不可直接相减——状态层可以逐例对比，任务层不行。

判什么、不判什么见 [`评测契约.md`](评测契约.md)；协议与命令见 [`评测方法.md`](评测方法.md)。

## 2. 与 v2 的可比性

| 层 | v2 | v3 | 差异来源 |
| --- | ---: | ---: | --- |
| 状态完成率 | 95/96 = 98.96% | 91/96 = 94.79% | 全部来自 2 个用例的模型波动（见下） |
| 任务完成率 | 98.96%（旧口径：状态 + 过程 + 依据） | 93.75%（新口径：再加合同） | 合同新增 1 次失败，其余同上 |

逐例对比：v2 唯一失败的是 `core-multistore-002` 第 2 次；v3 失败集合是 `core-multistore-002` 第 2 次、`core-multistore-005` 3 次、`core-write-005` 第 3 次、`core-multiturn-003` 第 3 次。

- `core-multistore-005` 在 v2 只是 1/3 失败，这一轮 3/3 失败——同一行为在两次运行里出现频率不同，属于模型侧的稳定性问题，不是断言造成的；
- `core-write-005` 与 `core-multistore-002` 的失败模式与 v2 完全相同（同样缺写、同样被 `INVALID_ARGUMENTS` 拒绝）；
- **断言真正新增的失败只有 1 次**：`core-multiturn-003` 第 3 次，状态全对、只错在逐轮答复。

所以"98.96% → 93.75%"这个落差里，断言贡献 1 次，其余 5 次是同一批不稳定用例的抖动。把两轮并排比完成率会得出错误结论，逐例看才对得上。

## 3. Core 六次失败逐条

| 用例 | 次 | 失败维度 | 证据 |
| --- | ---: | --- | --- |
| `core-multistore-005` | 1/2/3 | 状态 + 合同 | 读了 `get_listing(store-mu/SKU-8351)` 与 `get_listing(store-nu/SKU-8352)` 后**没有发起写入**；`set_listing_price` 调用缺失，`store-mu/SKU-8351` 仍是 69.00 |
| `core-multistore-002` | 2 | 状态 + 顺序 + 合同 | 同上：读完两家价格后停在读取阶段，`compare_listing_prices → set_listing_price` 顺序约束不成立 |
| `core-write-005` | 3 | 状态 + 依据 | `set_listing_price` 状态 `DENIED`，`failure_code=INVALID_ARGUMENTS`：模型把 `target_price` 写成 JSON 数字 `52.35`，工具 schema 要求字符串 |
| `core-multiturn-003` | 3 | 合同（仅） | 状态正确（72.00 落库）；第一轮"列出 store-xi 在售 SKU"的答复里 `SKU-8531` 既不在工具结果也不在答复中，`turn1.omitted: SKU-8532` |

前三条是同一个行为模式：**多店场景里读完两个价格就停住**。两次运行都在 `core-multistore-002` 上出现过，这一轮扩大到 `core-multistore-005`。

## 4. 断言是否真的在起作用

这一轮的价值不在数字，而在这三件事被看见了：

1. **逐轮答复**：`core-multiturn-003` 第 3 次在旧协议下会判通过（最终状态 72.00 正确、最终答复也提到了 72.00）。v3 下它失败，因为第一轮没把两个 SKU 都列出来。这是新断言唯一新增的失败，也正是它该抓的东西。
2. **实际入参进报告**：`core-write-005` 第 3 次的 `trace.tool_calls[2].arguments` 直接显示 `target_price: 52.35`（数字），不必回捞数据库就能看出拒绝原因。
3. **禁止调用**：4 个只读用例 × 3 次 = 12 次执行里 `forbidden_call` 命中 **0** 次。这条断言这一轮没抓到问题，但它现在的分母是 12 次执行而不是"0 次检查"——以前只读场景只有 `max_logical_writes: 0`，被拦下的写尝试根本不进判分。

Safety 分区同口径复核：17 次危险尝试、17 次被拦截、0 次落库、0 次未决、0 次敏感披露。与 v2 完全一致，说明新增断言没有把安全结论改松或改严。

Blind 分区的失败同样有信息：

| 用例 | 次 | 现象 |
| --- | ---: | --- |
| `blind-multistore-001` | 1/2/3 | 状态 `FAILED`：任务描述完整，模型仍发起 Input Request，而场景没有声明交互 → 运行器报 `requires a input interaction but none was declared` |
| `blind-composite-001` | 1 | 读到了 104.00（> 100），但没有发起改价，`store-rho/SKU-9161` 仍为 104.00 |
| `blind-read-001` | 1 | 答复依据失败：4 条期望事实（`SKU-9101`/`SKU-9102`/`47.00`/`53.00`）一条都没命中 |

`blind-multistore-001` 在 v2 里也是 3/3 失败，当时被记成"Invalid Gold"。这一轮复核：Gold 没错（store-chi 119 > store-phi 112，应把 chi 改为 114），错的是模型把可判定的任务当成需要追问。**这个用例的归因该从"Gold 有问题"改成"模型在可判定任务上多余追问"**。

`blind-read-001` 的答复原文没有进报告（见 §6 局限），所以只能记"4 条事实 0 命中"，不能断言模型答错了内容。

## 5. Clarification 为什么是 0%

18 次执行全部是 `RuntimeError: scenario clarify-* has unconsumed user interaction(s)` 或 `requires a input interaction but none was declared`——`status=FAILED`，不是判分失败。

原因与 v2 相同：模型用自然语言追问（"请指定要修改的店铺"），不产生结构化的 Input Request，而场景声明了 `interactions`，运行器等不到它。

这是**评测协议表达力的缺口**，不是模型缺陷：当前协议只有"结构化追问"这一种通过路径，无法表达"口头追问也算完成澄清"。改法是把这类场景改成独立判分项（运行结束且无写入、答复里问到缺失字段 → 通过），属于协议 v4 的范围，这一轮没有动，也没有为了让数字好看去改 Prompt。

## 6. 已知局限

1. **报告不存答复原文**。`trace` 只有事件、ToolCall、Operation 与最终状态，没有 Assistant 文本；隔离环境在用例结束时清理，事后只能重跑。`blind-read-001` 的答复内容、`core-multistore-005` 停下时说了什么，这一轮都无法复核。
2. **Blind 只换实体与条件组合**，不换决策结构。它证明"没有背下 Core 的答案"，不证明"能处理没见过的任务类型"。
3. **单轮 3 次重复不足以估方差**。`core-multistore-005` 在两次运行里是 1/3 与 3/3，说明 3 次的样本量太小；门禁的 ±2pp 容差应当用 3–5 轮重复的方差来定，而不是现在的经验值。
4. **`INVALID_ARGUMENTS` 的拒绝是产品行为，不是评测口径问题**。金额参数只接受字符串，模型写数字就被拒——语义正确的调用被判失败。这一轮保留原行为（改它会换 `system_fingerprint`、作废本轮基线），记录为待修。
5. **Contract 断言只覆盖状态看不见的字段**（金额、增量、原因码），`store_ref`/`sku` 不断言，理由是自由文本引用的同义写法不该判失败。这意味着"改错店但最后状态碰巧一致"这一类缺陷仍只能靠状态与目标归因兜底。

  uv run python -m eval.product_suite --split $split `
    --capability-manifest reports/product-operations-v3-manifest.json `
    --output reports/product-operations-v3-20261022-$split.json `
    --runtime-suite-result passed --e2e-result passed

uv run python -m eval.gates.derive_baseline --report reports/product-operations-v3-20261022-core.json `
    --output eval/gates/v3.json --gate-version v3 `
    --dataset eval/datasets/product_operations/core.yaml --allow-known-failures

    --report reports/product-operations-v3-20261022-core.json `
