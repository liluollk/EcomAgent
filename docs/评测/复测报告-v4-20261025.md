# 协议 v4 复测（2026-10-25，未完成）

**这一轮只跑完了 Clarification 一个分区。** Core / Blind / Safety / Regression 在启动后全部因 DeepSeek 返回 `402 insufficient balance` 失败（`/user/balance` 显示 `is_available: false`、`total_balance 0.00`），属外部额度问题，不是评测设施缺陷。因此本轮**没有** v4 的 Core 基线，也**没有**派生 `eval/gates/v4.json`。

数据修正：§2 的数字是 scorer v4 判的；§3 复核轨迹后补了 scorer v5（补全点按路径取）。用同一份轨迹重算，**通过数不变（15/18）**，`no_ask_before_supply` 3 → 0——变的是失败原因的归因，见 §3。

## 1. 协议 v4 改了什么

| 改动 | 原因 |
| --- | --- |
| 新增 `clarification` 场景声明 + `ClarificationScorer` | v3 只认"结构化 Input Request"一条通过路径，模型用自然语言追问时整例被判失败（18/18），这是协议表达力缺口，不是模型缺陷 |
| 报告 `trace.messages` 输出脱敏答复原文 | 失败归因需要；此前"答复依据未命中"只能记成"0 命中"，分不清答错内容与答错措辞 |
| `normalize_amount` 接受 JSON 数字 | 模型把 `target_price` 写成 `52.35`（数字）时被 `INVALID_ARGUMENTS` 拒；语义正确的调用不该判失败 |
| 门禁冻结 `system_fingerprint`，新增 `SYSTEM_FINGERPRINT_MISMATCH` | 报告之间互相一致不等于描述当前系统；能力清单变了必须重新派生基线 |
| `capability_manifest` 去掉硬编码 `scorer_version="v3"` | CLI 生成的清单与 `EvalConfig` 版本不一致，会让指纹描述错误的判分版本 |

`SCHEMA_VERSION` 2 → 3 → **4**，`REPORT_SCHEMA_VERSION` 7 → **8**，Scorer v4 → **v5**。v4 的 Core/Blind 语料哈希随 `schema_version` 变化，**不能**与 v3 数字相减；v5 只动澄清判分的补全点，语料未变，但判分版本变了，报告指纹跟着变，需重跑取新数。

## 3. 剩下 3 次为什么失败

三次都在 `clarify-store-*`，链路完全相同（下面按轨迹逐条对过，不是推测）：

1. 用户只说 "把 SKU-3003 改到 88.00 元"，店铺缺失；
2. 模型**先口头问了**（"SKU-3003 在 store-alpha 和 store-beta 两个店铺都有上架，你未指定店铺，需要确认改价范围"），同一轮里又对两家店各发一次 `get_listing`；
3. 两家店中的第二家被参数来源守卫拦下（读/写目标必须来自本轮用户消息），抛 Input Request 要求选店；
4. Runner 用场景声明的 `{store_ref: store-alpha}` 应答，Run 恢复；
5. 模型重试时**再次**请求输入，而场景只声明了一次供值 → `requested more input than the scenario supplies`，整例 `FAILED`。

这一段上一版写错了：原文说"模型没有口头追问"，实际轨迹里第 5 条消息就是追问。错的不只是文字——澄清判分当时把补全点定在"最后一条用户消息"，而结构化应答路径下会话里只有一条用户消息，于是第 5 条的追问落到了补全点之后，三次都被记成 `no_ask_before_supply`。**指标在描述一件没发生的事。**

scorer v5 把补全点改成按路径取（第二条用户消息 / `RUN_WAITING_INPUT` 之后的 `RUN_RESUMED`）。用同一份 v4 轨迹重算：18 次全部识别为"补全前追问过"，`no_ask_before_supply` 从 3 降到 **0**，通过数仍是 **15/18**（这三次依旧 `FAILED`，卡在第 5 步的供值次数上）。改的是归因，不是通过率。

所以这三次也不是"模型猜店铺被判错"，而是"模型问过、拿到一次应答、又问一次，场景只给一次供值"的协议边界。要让它通过，得允许同一轮内重复使用已声明的值（可能形成追问循环），或把场景改成声明多次供值（当前 schema 禁止同一用户消息挂多个交互）。两种改法都会削弱"模型不该反复追问"这条信号，本轮没有动。

## 4. 场景改了什么，为什么不算"改题凑数"

六个澄清场景的**第二轮用户消息**由 "改 store-alpha 的。" 改成 "把 store-alpha 的 SKU-3003 改到 88.00 元。"

原因是一处有意为之的产品规则：`agents/product_operations/input/provenance.py` 明确 `del history`——**旧对话不作为写目标的证据来源**，`store_ref`/`sku`/`target_price` 必须出现在本轮用户消息里。第一版场景只让用户补一句店铺，运行时就会因为"SKU 不在本轮消息里"再次要求输入，任务永远做不完。

这条规则本身值得单独记一笔：真实对话里用户补一句"改那家店的"很常见，当前实现会要求重述完整目标。它属于产品取舍，不是评测口径问题；本轮按现状设定场景，没有改产品。

## 5. 澄清判分怎么判，边界在哪

两条顺序事实，都只看时序不看措辞（v5 起补全点按路径取）：

1. **补全前追问过**：补全点之前，存在一条 Assistant 答复在追问缺失字段；
2. **补全前没写过**：第一条写类 ToolCall 出现在补全点之后。

补全点：场景用第二条用户消息补全就取那条消息；模型走结构化 Input Request 就取 `RUN_WAITING_INPUT` 之后的 `RUN_RESUMED`（确认类恢复没有这个前置，不算补全）。

"追问"的判定是"提到缺失字段的说法 + 有请求措辞"，**不要求问号**——实测答复大量是陈述式："要改价还缺一个关键信息：目标价格。请告诉我希望设为多少。" 只认 `？` 会把真实追问判成没问（第一版就是这么错判 11 次的）。

已知边界：

- 说法表（店铺/门店/store、SKU/商品、价格/售价/目标价…）覆盖不到的同义写法会漏判；
- 表外措辞造成的**误判方向是"判没问"**，不会把"没问"判成"问了"；
- 它判的是"有没有在补全前索要缺失信息"，不判追问质量。

## 6. 待办（需要额度）

补记一处设施修正：本轮的探测只打了 `GET /models`，额度为零时它照样返回 200，于是 `core` 先跑满 20 个用例、再跑满 96 个用例才整轮作废。现在探测改成发一次 `max_tokens=16` 的最小对话请求——额度/鉴权问题会在第一个 case 之前以 `provider probe failed: HTTP 402 ...` 停下，报告里只有一条基础设施错误、零执行数。

scorer 升到 v5 之后，下面这轮复跑要连 Clarification 一起重跑（18 次，成本很低），报告与门都用 v5 命名。清单按当前代码重新生成（`uv run python -m eval.capability_manifest --output reports/product-operations-v5-manifest.json`）。`reports/` 不入库，换机器要自己再生成一次。

**指纹在这轮之后变了一次，引用时注意。** Windows 上用 `Path.write_text` 改数据集会把 `\n` 翻成 `\r\n`，同步脚本又按原始字节算哈希，于是 `core`/`blind` 的冻结哈希被冻成 CRLF 的值；`.gitattributes` 声明的是 `eol=lf`，CI 检出成 LF，`test_frozen_hashes_match_file_bytes` 在 CI 上必红（本地因为工作区是 CRLF 反而绿——这就是 run #6 挂掉的那一步）。修法是把数据集归一成 LF 再按 LF 字节重算哈希：

- `core_sha256` `11c667d4…` → `b0d20e0e…`，`blind_sha256` `89735a8d…` → `bc3b5e12…`（**只有换行符变了，YAML 内容零改动**）；
- `capability_fingerprint` `91ae646b…` → `109f2d2e…`；
- 本文件第 1~5 节的 v4 数字跑在旧字节上，与 v5 不可直接相减；v5 一轮会同时产出新的补全点与新的字节基线，不用拼两轮。

```powershell
$env:RUNTIME_TEST_DATABASE_URL = "postgresql+asyncpg://runtime:runtime@localhost:5432/agent_runtime_eval_run_test"
$env:EVAL_BASE_URL  = "https://api.deepseek.com"
$env:EVAL_MODEL     = "deepseek-flash"
$env:EVAL_API_KEY   = "<key>"

# 1) 重跑五个分区
foreach ($split in "core","safety","regression","blind","clarification") {
  uv run python -m eval.product_suite --split $split `
    --capability-manifest reports/product-operations-v5-manifest.json `
    --output reports/product-operations-v5-20261025-$split.json `
    --runtime-suite-result passed --e2e-result passed
}
# 2) 派生 v5 门并过门禁
uv run python -m eval.gates.derive_baseline --report reports/product-operations-v5-20261025-core.json `
    --output eval/gates/v5.json --gate-version v5 `
    --dataset eval/datasets/product_operations/core.yaml --allow-known-failures
uv run python -m eval.gates.check_release --gate eval/gates/v5.json `
    --report reports/product-operations-v5-20261025-core.json `

```
