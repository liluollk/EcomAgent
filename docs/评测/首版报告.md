# 核心评测报告

> 本报告只记录真实执行结果，不包含估计数字。商品 Agent 使用 DeepSeek `deepseek-flash`、`temperature=0`、每个任务重复 3 次；API Key 不写入仓库或报告。
>
> **试卷版本说明**：本文件记录的是 **30 条 Core** 试卷（90 次执行）上的历史结果，用于说明评测集审计与早期迭代。当前数据集已扩展为 **32 条 Core**（96 次执行，五分区共 60 例），`core.yaml` 的字节哈希已变化，因此本节的历史 `benchmark_fingerprint` 与数字**不代表当前试卷**；当前试卷必须重新跑一遍才能形成新基线，在此之前不要把 58.89% / 67.78% / 75.56% 描述为最新效果。

## 1. 当前协议

- Core：30 个不同任务，90 次执行；
- 主指标：权威最终状态驱动的任务完成率；
- 稳定性：连续 3 次全部完成的任务数；
- Clarification、Safety、Runtime 和 Recovery 独立报告；
- Blind 在 Core 优化完成前不运行。

运行日期：2026-10-10。

| 30 | 90 | 53 | 58.89% | 15/30 | 0 |

当轮文件哈希验证通过，协议执行无基础设施错误。报告保存在未跟踪文件 `reports/core-baseline-20261009.json`，协议指纹为 `aeb3a9c34130e0ceed2b75b7b4258a574975a814fcafc14cc3de2209720b6bec`。

按任务族拆分：

| 任务族 | 成功执行/总执行 | 稳定通过任务 |
| --- | ---: | ---: |
| 商品查询 | 12/12 | 4/4 |
| 明确目标价改价 | 13/18 | 3/6 |
| 相对金额或百分比改价 | 17/18 | 5/6 |
| 多店比较后选择目标 | 0/18 | 0/6 |
| 搜索或查询后再改价 | 3/12 | 1/4 |
| 多轮修正与约束保持 | 8/12 | 2/4 |

结果显示基础查询、明确改价和相对计算已经较稳定，主要失败集中在多店决策和复合任务。20 次执行停在 Input Request，17 次虽然 Run 完成但没有达到目标写入状态。Trace 显示两类主要原因：模型读取或比较后直接结束；模型把 ToolResult 中的内部店铺标识用于后续调用，参数来源校验无法把它关联到用户明确说出的店铺名称，因此按 fail-closed 规则要求补充输入。

审计 Trace 后确认，6 条多店写任务中有 4 条没有在用户消息中点名候选店铺范围，却期望 Agent 自动选择并写入，与项目“关键写入范围缺失时 fail-closed”的规则冲突。这 4 条属于 Invalid Gold，不是 Agent 失败。因此本轮 `58.89%` 只用于发现评测集缺陷，不能作为简历 Baseline，也不能与后续结果计算提升。

修正只补齐题面中的候选店铺名称，不修改预期状态或 Scorer；同时增加自动化约束，保证所有多店写任务都明确给出候选店铺。该轮只用于审计评测集，不进入前后提升计算。

## 4. 已验证的工程事实

### 4.1 Core 优化结果

针对 Baseline 中“读取或比较后直接结束”和“后续调用复制内部 ID”两类 Trace，v4 只修改 Prompt、Skill 与 Tool Schema，并重新运行同一 Core：

| 版本 | 成功执行/总执行 | 任务完成率 | 稳定通过任务 |
| --- | ---: | ---: | ---: |
| v3 Baseline | 61/90 | 67.78% | 14/30 |
| v4 | 68/90 | 75.56% | 17/30 |

两轮 `benchmark_fingerprint` 都是 `535bce3f7207e82cc82abfb3c0e5638fb8e3c08e284b1dd85930fc36496ed73e`，基础设施错误均为 0。净增 7 次成功，提升 7.78 个百分点。

优化主要命中目标任务：复合任务从 3/12 提升至 9/12，多店决策从 12/18 提升至 16/18；同时相对改价从 16/18 降至 12/18，说明模型仍有明显波动，不能把结果解释成所有任务族全面提升。v4 报告保存在未跟踪文件 `reports/core-after-v4-20261010.json`。

### 4.2 Blind 一次性检查

冻结 v4 后首次运行 10 个 Blind 场景、30 次执行，原始结果为 19/30（63.33%），稳定通过任务 5/10，基础设施错误 0。该结果低于 Core，说明优化后的能力在新题面上仍不稳定。

揭封后发现 `blind-multistore-001` 没有在用户消息中给出候选店铺，却要求 Agent 自动选择并写入，违反关键写入范围 fail-closed 规则，属于 `Invalid Gold`。本项目不修改后重跑并继续称其为 Blind，也不事后删除该题重新计算一个更高分；原始结果保留为评测集审计证据。`blind-read-001` 则暴露了真实架构问题：只读链路沿用写参数 Provenance 约束，导致 Agent 无法稳定把搜索结果中的多个 SKU 继续用于快照读取，应进入后续 Bad Case。

### 4.3 Safety

v4 在独立 Safety 集运行 8 个场景、24 次执行（当时 Safety 集为 8 例，现为 10 例）：模型发起 10 次危险调用尝试，执行层拦截 10 次，实际危险副作用为 0，基础设施错误为 0。该结果只说明当前用例中的权限与 Business Policy 边界生效，不与 Core 完成率合并，也不包装成生产安全结论。报告保存在未跟踪文件 `reports/safety-v4-20261010.json`。

此前真实模型诊断还暴露过多店请求的参数来源校验误拦截合法目标，以及 Tool 描述与 `AUTO_EXECUTE` 的执行语义冲突；这些修复保留为失败驱动迭代证据。

### 4.4 简历口径

> 构建基于业务终态的 30 条 Gold Case 评测集，固定模型、Scorer 与重复运行协议，通过 Tool 调用轨迹归因并优化 Prompt、Skill 和 Tool Schema，使 Core 任务完成率从 67.78%（61/90）提升至 75.56%（68/90）；以独立 Safety 用例验证权限与 Business Policy 在危险调用下仍能阻断实际越权写入。

这条只把同一 Core 上的前后结果称为“优化效果”，不称为线上收益或泛化结论。面试追问时必须主动说明 Blind 原始结果 19/30、其中一条 `Invalid Gold`，以及只读 Provenance 暴露的后续问题。
