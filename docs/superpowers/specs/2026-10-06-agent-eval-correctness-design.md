# Agent Eval 正确性修正设计

## 目标

让商品运营 Agent 的 Eval 同时验证最终业务结果与执行过程，并检查关键回答是否有运行证据支撑；确保场景被真实执行、失败不被统计口径隐藏、指标分母与含义一致。

## 设计原则

- 保留现有 Eval 架构、Runner、Scorer 和报告结构，不重写整个评测模块。
- 场景数据是可执行用例：用户对话、补充信息、确认/拒绝、操作者权限、初始状态和预期结果都必须明确表达。
- Runner 不推断用户选择、不代替用户确认；只执行场景声明的输入与决策。
- 结果判分查看平台权威最终状态；过程判分查看工具调用、授权决策、确认和恢复轨迹。合法替代路径不应因工具顺序细节被误判。
- 回答依据判分使用确定性、场景声明的关键事实断言，并与实际工具/平台证据比对；不引入另一个 LLM 作为 Judge，也不宣称穷尽所有自然语言幻觉。
- Provider/数据库不可用单独报告；Agent 或 Runtime 导致的任务失败不得从任务完成率中消失。
- 完整用户消息内容参与场景指纹；冻结集变更必须同步更新 schema/manifest，并由测试检查。

## 评测维度

1. **结果正确**：最终商品状态、逻辑写次数与场景期望一致。
2. **过程正确与安全**：调用目标、授权、必要步骤、澄清/确认决定、禁止副作用和恢复路径符合场景约束；尝试、拦截、实际副作用分开报告。
3. **回答有依据**：场景声明需要回答的关键事实必须出现在最终答复中，且数值/实体与捕获的运行证据或权威最终状态一致。
4. **统计可信**：误拒只在合法写决策机会中计算；恢复率只统计声明需要恢复或实际遇到 UNKNOWN 的样本；质量失败与基础设施错误分开。

## 执行与数据模型

- Eval 场景需表达真实用户输入轮次、Input Request 的显式答案、Confirmation Request 的接受/拒绝决定，以及该执行者的权限和店铺范围。
- 连续用户轮次应绑定到同一 Session；Runtime 发起的补充信息和确认等待仍在原 Run 中恢复。
- 执行者授权采用场景显式声明；缺省权限按拒绝处理，不沿用全权限默认值。
- 捕获 Run 内用户可见的最终答复、工具调用与结果、事件和权威最终业务状态。
- Run 的 FAILED/CANCELLED 属于任务未成功；连接/服务不可用属于基础设施错误，单独列出并标为无法评价模型行为。

## 非目标

- 不用 Eval 替代 Runtime 的确定性安全单测、集成测试和故障注入套件。
- 不将 Mock 场景结果包装成真实运营收益或生产指标。
- 不引入 LLM Judge、统计平台、分布式评测基础设施或模型路由。
- 本轮不触发真实模型请求。

## 验收标准

- 真实 Runner 测试证明后续用户轮次、显式 Input 答案和确认/拒绝决定确实影响执行；未声明答案或决定时不得自动补齐。
- 场景能构造无写权限和无目标店铺权限的真实成员状态，拒绝写入且最终状态不变。
- 改动任何用户消息文本都会改变协议指纹。
- 任务失败、误拒、恢复成功率的分子/分母由测试验证，样本不适用时返回 null 而非空真通过。
- 回复事实只有在与捕获证据一致时才能通过；用例缺少需要验证的回答事实时报告明确标注不适用。
- 所有产品 Eval 场景均有可审查的结果、过程和回答断言；冻结集哈希和 manifest 一致。
- `tests/eval` 全部通过；不调用在线 Provider。
