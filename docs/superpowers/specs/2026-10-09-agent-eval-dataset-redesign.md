# Agent 核心评测集设计

## 1. 目标

本项目通过一组固定、可复现的商品运营任务，回答一个核心问题：Agent 是否真正完成了用户要求的业务任务。

简历和面试只把核心任务完成率作为主指标。澄清、安全、Runtime 恢复分别验证，不进入核心任务完成率分母。评测结果只代表当前模型、Prompt、Tool、受控商品状态和固定样本，不描述为生产流量指标。

## 2. 唯一数据口径

商品评测数据分为五类：

```text
eval/datasets/product_operations/
├── core.yaml            # 30 条固定核心 Gold Case
├── blind.yaml           # 10 条优化期间不运行的盲测任务
├── clarification.yaml   # 6 条缺参澄清与恢复任务
├── regression.yaml      # 真实 Bad Case 修复后的回归任务
├── safety.yaml          # 越权、规则绕过和敏感信息任务
└── manifest.json
```

- `core`：先冻结，再跑 Baseline；基于失败 Trace 优化后，只在协议不变时复跑并计算 `X% → Y%`。
- `blind`：核心集优化结束后只运行一次，用于检查是否只对固定题目过拟合；查看结果后不得继续把它称为未见数据。
- `clarification`：验证关键参数缺失时的追问、Input Request 和恢复，不进入核心完成率。
- `regression`：只收录真实运行中出现、已归因并修复的 Bad Case。
- `safety`：验证危险调用尝试、执行层拦截和实际危险副作用，不与核心完成率合并。

不再使用 Development、Held-out 或 Frozen Test 作为对外叙事。

## 3. 核心 Gold Case

`core.yaml` 固定 30 个不同用户目标：

| 任务族 | 数量 | 主要变化 |
| --- | ---: | --- |
| 商品查询与状态查询 | 4 | 单商品快照、跨店价格、店内搜索、状态与价格 |
| 明确目标价改价 | 6 | 整数、小数、保持币种与状态、指定不相关商品不变 |
| 相对金额或百分比改价 | 6 | 上调、下调、百分比计算、精确到分 |
| 多店比较后选择目标 | 6 | 较高、较低、追平、固定目标、不同商品比较 |
| 搜索或查询后再改价 | 4 | 定位、读取、计算、写入的组合任务 |
| 多轮修正与约束保持 | 4 | 最新目标、重复关键范围、保留禁止修改约束 |

每条任务必须包含初始权威状态、Actor 权限、用户消息、期望最终状态、最大逻辑写次数，以及适用的回答证据和允许副作用。只替换店铺、SKU 或数字不算新任务。

## 4. 核心指标

固定模型配置为 DeepSeek、`temperature=0`、每条任务重复 3 次：

```text
30 个不同任务 × 3 次 = 90 次执行
任务完成率 = 成功执行次数 / 90
稳定通过率 = 连续 3 次全部成功的任务数 / 30
```

重复运行用于观察非确定性稳定程度，不能描述成 90 个独立场景。报告必须同时给出任务数、重复次数、成功次数和总执行次数。

任务完成以权威业务状态为主：

- 目标 Listing 达到期望状态；
- 不相关 Listing 保持不变；
- 逻辑写入次数不超过期望；
- Run 正常完成；
- 查询类回答的关键事实能由 ToolResult 或最终状态证明。

允许模型采用不同但合法的 Tool 路径。只有业务语义确实要求先查询再计算时，才声明必要的工具先后关系。

## 5. 比较流程

1. 冻结 `core.yaml`、Scorer、模型配置、Prompt、Skill 和 Tool Schema 的版本信息。
2. 运行 90 次得到首个 Baseline。
3. 查看失败 Trace，按模型决策、Prompt/Skill、Tool Schema、参数溯源、业务处理或评分错误归因。
4. 只修复能够由失败证据支持的问题，并把已修复问题加入 Regression。
5. 在完全相同的核心协议上复跑，得到真实的 `X% → Y%`。
6. 优化结束后运行 10 条 Blind Case；Blind 只作过拟合检查，不参与继续调参。
7. Clarification、Safety、Runtime 和 Recovery 分别运行并分别报告。

如果场景、Scorer、模型配置或影响决策的 Prompt/Tool 版本发生变化，协议指纹必须变化，不直接与旧结果比较。

## 6. 独立验证

- Clarification：报告完成次数和失败类型，不并入核心任务完成率。
- Safety：分别报告危险写入尝试、执行前拦截和实际危险副作用；实际未授权副作用必须为 0。
- Runtime/Recovery：通过确定性套件检查等待与恢复、UNKNOWN 后回查、幂等重放和最终状态一致性。
- Infrastructure Error：单独报告，不计为模型成功或失败；存在基础设施错误的报告不能形成有效 Baseline。

## 7. 非目标

- 不测 Token、延迟和成本；
- 不引入综合总分或 LLM-as-Judge；
- 不为得到好看的提升幅度故意加入越权提示或错误期望；
- 不把重复执行包装成更多独立任务；
- 不把受控 Mock 商品环境结果包装成线上业务效果；
- 不修改 Runtime 状态机或扩展商品业务范围。

## 8. 验收标准

1. Core 恰好包含 30 条信息完整、合法、无故障注入的业务任务，且不含 Input/Confirmation Interaction。
2. Core 六个任务族的数量固定为 `4/6/6/6/4/4`。
3. Blind 恰好包含 10 条与 Core 实体隔离、任务组合不重复的合法任务。
4. Clarification 独立包含 6 条真实缺参任务，每条声明 Input Interaction。
5. Safety、Regression、Runtime 和 Recovery 保持独立口径。
6. Core 与 Blind 文件均通过 SHA-256 固定，运行前检测漂移。
7. JSON 报告同时提供执行级任务完成率和场景级 `3/3` 稳定通过数。
8. CLI、Manifest、Release Gate、自动化测试和中文评测文档使用同一套分区名称。
9. 真实 Baseline 必须来自 30 条 Core 的 90 次有效执行，且基础设施错误为 0。
10. `reports/` 继续保持未跟踪，不提交凭据或真实运行报告。
