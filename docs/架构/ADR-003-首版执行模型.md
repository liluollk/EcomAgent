# ADR-003：首版执行模型——单 API 进程、单 Runtime Executor

- **状态：** 已接受并已实施
- **决策日期：** 2026-10-19
- **适用范围：** Run 调度、并发控制、进程重启恢复、写操作安全、E2E 与评测装配
- **不包含：** 多实例水平扩展、跨进程任务队列、租约 / 心跳 / fencing token、按 Run 亲和的独立执行进程

## 1. 决策摘要

首版明确限定「**单 API 进程、单 Runtime Executor**」，不支持多个实例并发抢占同一批任务。执行模型因此退化为进程内推进：

```text
API 创建 Run(QUEUED)
  → 进程内 RunExecutor 以 state_version CAS 把 Run 推入 RUNNING
  → RunDriver.advance 推进到下一个持久边界
  → 关键节点由 ToolExecutor 自己提交(begin / record_result 各一个短事务)
  → WAITING_INPUT / WAITING_CONFIRMATION 时自然停下,等用户响应
  → 用户响应提交后唤醒执行器,继续推进同一个 Run
  → 进程重启时扫描非终态 Run:先回查不确定的外部写,再继续推进
```

删除的机制：独立 Worker 进程、`RunJob` 表、租约（`lease_token` / `lease_expires_at`）、心跳续租、fencing token、`LeaseSweeper`。

保留并强化的机制：`Workspace / Session / Run` 模型、Run 状态机、持久化 Message / ToolCall / Operation / AgentEvent、人工确认后继续执行、`UNKNOWN → Reconciliation`、进程重启后的任务恢复、`state_version` CAS。

结论先行：**删掉 Worker/Job/租约不影响外部写入的可靠性**。写入安全由持久化 `Operation`、稳定 `operation_id`、幂等键与回查保证；Job/租约解决的是"多个执行者之间谁干活"，不是"外部系统到底写没写"。这两件事此前被同一套机制承载，容易被混为一谈。

## 2. 为什么要删，而不是保留但不用

原实现中，`RunJob` + 租约 + 心跳 + fencing token 是一个完整的多实例抢占方案：

| 机制 | 解决的问题 | 首版是否需要 |
|---|---|---|
| `RunJob` 表 | 跨进程分发任务、崩溃后可重领 | 否。数据库里的 `QUEUED` Run 就是队列 |
| 租约 + 心跳 | 判断执行者是否仍活着 | 否。只有一个执行者，进程活着就活着 |
| fencing token | 拒绝失租执行者的迟到提交 | 否。没有"第二个执行者"，只有"上一次进程" |
| `LeaseSweeper` | 回收过期租约并重新入队 | 否。由启动恢复扫描替代 |
| `attempt_count` 退避 | 避免坏任务被反复领取 | 部分。保留为 `RunAttempt` 预算 |

如果保留这套机制却只跑一个实例，代价是实打实的：

1. **多一条必须被测试覆盖的状态链**：`PENDING → LEASED → DONE/DEAD` 的每个分支都要写用例，而它在本部署形态下永不产生新行为；
2. **多一条可能出错的时间维度**：心跳间隔、租约时长、时钟漂移、Sweeper 扫描周期，这些参数在单实例下没有可观测收益，却会引入偶发失败；
3. **掩盖真正的并发问题**：有了 fencing token，容易误以为"提交安全已经解决了"，从而放松对 `state_version` CAS 的依赖。实际上 fencing 只能约束"谁有资格提交"，不能约束"两个提交之间的读改写竞争"。

因此选择的不是"暂时不用"，而是**从代码里删除**。首版不接受多实例，就不维护多实例的机制。

## 3. 替代方案与取舍

### 3.1 方案 A：保留 Job/租约，部署时只起一个 Worker（未采纳）

改动最小，但把"未使用的复杂度"永久留在仓库里。评审者无法从代码判断系统实际支持几个实例，也无法判断哪些分支是死代码。首版的价值在于边界清晰，不在于保留扩展点。

### 3.2 方案 B：改用 Redis / Celery 等外部队列（未采纳）

引入新的基础设施依赖，仍然需要解决幂等与回查；而首版真正稀缺的不是吞吐，是"一条 Run 能被正确推进并恢复"。外部队列不减少任何领域代码。

### 3.3 方案 C：进程内执行器 + PostgreSQL 单写者断言（采纳）

数据库既是状态源也是队列。执行器在进程内、与 API 同生命周期。多实例被一条 advisory lock 显式拒绝，而不是"约定不要起两个"。

## 4. 目标组件

| 组件 | 位置 | 职责 |
|---|---|---|
| `RunExecutor` | `runtime/execution/executor.py` | 领取（CAS）、推进、收尾 Attempt、失败预算、恢复扫描、后台兜底循环 |
| `RunDriver`（Protocol） | 同上 | `advance(claim)` / `reconcile(run_id, workspace_id)`，由组合根实现 |
| `RunClaim` | 同上 | 一次推进的凭据：`run_id / workspace_id / actor / membership / attempt_id / attempt_no`；**不含租约语义** |
| `RunNextStep` | `runtime/persistence/base.py` | 执行器内部调度指令：`ADVANCE` / `RECONCILE` |
| `SingleWriterLock` | `runtime/execution/single_writer.py` | PostgreSQL advisory lock（固定键），启动时竞争一次，失败 fail-fast |
| `ExecutorHost` | `apps/api/executor_host.py` | API 进程内持有执行器 + 商品域 driver 的生命周期 |
| `ProductDriverRegistry` | `apps/scripted_e2e.py` | E2E/脚本化装配下按 `(workspace, actor)` 组装 `ProductApplication` 作为 driver |

`RunExecutor` 不感知领域语义。`ProductApplication` 实现 `RunDriver`；`Runtime.advance(claim)` 是它的内核回调。

## 5. 并发控制只剩两层

### 5.1 `Run.state_version` CAS（每次推进）

所有 Run 状态迁移都走 `RunRepository.compare_and_set_status`：`WHERE id = ? AND workspace_id = ? AND state_version = ?`，成功时 `state_version + 1`。零行更新即表示有人先推进了，本次推进必须放弃。

这一层不可省。它不是为多实例准备的，而是为**同一个进程内的并发路径**准备的：

- API 路由提交消息后唤醒执行器，同时后台兜底循环也在扫描 `QUEUED`；
- 用户连续点两次"接受确认"；
- 恢复扫描与请求内同步推进同时命中同一个 Run。

没有 CAS，这些路径会产生同一 Run 的双重推进与重复事件序号。

### 5.2 进程级单写者锁（每次启动）

`SingleWriterLock` 在 `RunExecutor.start()` 里获取 PostgreSQL advisory lock（固定键 `0x52554E45`），获取失败抛 `SingleWriterViolation`，进程拒绝启动。

它**不是 per-task 租约**：一个进程生命周期只竞争一次，不参与任务调度，也不需要在推进过程中续期。它只回答一个问题——同一数据库上是否已经有执行器在跑。

## 6. 恢复语义

`RunExecutor.recover()` 在启动时扫描 `QUEUED / RUNNING / WAITING_RECONCILIATION` 三类 Run，处理顺序不可交换：

```text
1. 收尾上次进程遗留的 RUNNING Attempt → ABANDONED(failure_code=EXECUTOR_RESTART)
2. 对存在 EXECUTING/UNKNOWN Operation 的 Run:先回查(必要时 CAS 到 WAITING_RECONCILIATION)
3. 回查消除不确定性后,继续推进同一个 Run
4. 其余 RUNNING 一律视为上次中断 → CAS 回 QUEUED → 推进
5. QUEUED 直接推进
```

关键判断：

- **启动时的 `RUNNING` 不等于"正在执行"**。进程内只有本执行器能推进 Run，新进程启动时不可能存在并发推进者，因此 `RUNNING` 一定是上次崩溃遗留；
- **`WAITING_INPUT` / `WAITING_CONFIRMATION` 不在恢复集合内**。它们等的是用户，不是执行能力；重启不应替用户作答，也不应让 Run 卡在无人推进的状态——用户响应时会重新入队；
- **先回查再推进**。若先推进，Agent Loop 会把"可能已生效的写"当成未发生，从而重复写外部系统。顺序是正确性要求，不是优化。

原 `LeaseSweeper` 的两项职责在这里各有归属：回收过期租约 → 由"进程重启"触发；把 Attempt 标为 `ABANDONED` → 由 `_abandon_open_attempts` 完成。第二项曾一度无人承接，会让审计视图永久停在"正在执行"。

## 7. 写操作安全不受影响

| 风险 | 保障机制 | 是否依赖 Job/租约 |
|---|---|---|
| 重复逻辑写 | 稳定 `operation_id` + 平台幂等键 | 否 |
| 写入已生效但响应丢失 | Operation `EXECUTING/UNKNOWN` + `Reconciliation` 先回查 | 否 |
| 已取消/已挂起的 Run 被追加新副作用 | `ensure_run_executable`（写操作进入执行边界前 Run 必须仍 `RUNNING`） | 否 |
| 迟到写回执把已取消的 Run 复活 | 回执照常记账（外部事实），Run 迁移由 `state_version` CAS 裁决，回执不驱动状态 | 否 |
| 两个推进者同时提交 | `state_version` CAS | 否 |
| 进程在外部调用期间崩溃 | `EXECUTING` 即"可能已执行"的唯一判据，重启后先回查 | 否 |

`ensure_run_executable` 取代了原 `ensure_write_fencing`：不再校验租约，只校验"Run 是否仍有执行资格"。首版不存在"租约被别人接管"的场景，真正需要拒绝的是用户取消、Run 已终态或已挂起时**新发起**的副作用。已经发出、随后才到达的回执不走这道校验——外部写可能已经发生，拒绝记账只会让权威状态与平台事实背离；这类回执只更新 Operation/ToolCall，Run 状态迁移仍由 `state_version` CAS 裁决，因此取消中的 Run 不会被回执拉回活跃状态。

## 9. 后果

### 9.1 已知限制（明确接受）

1. **无水平扩展**：同一数据库只能有一个 API 进程持有执行器。第二个进程启动会被 advisory lock 拒绝，而不是降级为只读；
2. **执行与 API 共享生命周期**：API 进程重启会中断正在推进的 Run，由恢复扫描接管；长任务与请求共享同一事件循环，需要靠 checkpoint 保证不长时间占用事务；
3. **无跨进程优先级与配额**：所有 Run 在一个进程内串行领取，吞吐上限是单进程的模型与工具调用速度；
4. **恢复是"启动时"而非"持续"**：运行期间没有定期扫描非终态 Run 的机制。若一次推进异常退出而进程未重启，兜底循环仍会通过 `QUEUED` 扫描捡回；但停在 `RUNNING` 的 Run 只有重启才会被重新解释。

第 4 条是首版最需要关注的运维约束，已写入 §6 与验收用例。

### 9.2 未来演进路径

需要多实例时，恢复的应是"分发"而不是"抢占"：

1. 保留 `state_version` CAS 与 `Operation`/回查语义（这两层与实例数无关）；
2. 以 `SKIP LOCKED` 的 Run 领取替代 advisory lock，租约只在领取粒度上引入，且必须配 fencing 或 CAS；
3. 恢复扫描改为周期性任务，覆盖"进程活着但推进卡死"的情况。

演进时不得回退的部分：外部写的幂等与回查、`EXECUTING` 作为不确定写的判据、恢复时"先回查再推进"的顺序。

## 11. 非目标

- 不承诺任意外部系统上的 exactly-once；目标是不重复**逻辑**写入，无法消除的不确定性优先停止；
- 不提供任务优先级、并发上限、租户配额；
- 不提供执行器与 API 的独立扩缩容；
- 不为"将来可能的多实例"预埋未使用的抽象。
