# ADR-002：商品运营模块化单体与平台适配边界

- **状态：** 已接受，尚未实施
- **决策日期：** 2026-10-12
- **适用范围：** 商品运营 Agent、Runtime ToolBinding、PreToolUse 业务扩展、平台 Adapter 与组合根
- **不包含：** 微服务拆分、动态插件系统、通用 Workflow Engine、Multi-Agent、真实第三方平台上线承诺

## 1. 决策摘要

项目采用“模块化单体”方案：

1. 保持一个仓库、一个 FastAPI 应用、一个 Runtime、一个数据库和一次部署；
2. Runtime 只承担 Session/Run、模型循环、Tool 执行、权限控制、确认、幂等、恢复与事件；
3. 商品运营按商品查询、价格、库存、商品状态划分业务模块；
4. Tool 是模型可调用的规范化业务契约，业务服务负责具体业务动作；
5. 平台差异通过小粒度 Gateway 和 Adapter 收敛；
6. Tool 的 PreToolUse 扩展与写执行目标按 Tool 绑定，不再由商品 Agent 全局共享；
7. 多平台路由由店铺的平台绑定决定，Runtime 不认识淘宝、京东、抖音等业务概念；
8. 仍采用显式注册和依赖注入，不引入运行时插件发现。

本 ADR 只冻结目标边界。当前源码仍是第一版商品改价实现，不能把本文目标设计描述成已经落地。

## 2. 为什么不是微服务

“业务模块”只表示代码职责边界，不表示独立进程或独立部署。

```text
一个 FastAPI 应用
  ├─ 一个 Runtime
  ├─ 一个 ProductOperationsAgent
  │   ├─ 商品查询模块
  │   ├─ 价格运营模块
  │   ├─ 库存运营模块
  │   └─ 商品状态模块
  └─ 多个平台 Adapter
```

业务模块之间仍然通过 Python 对象和函数调用，不引入 HTTP/RPC、消息总线或独立数据库。

## 3. 当前代码事实

截至本 ADR：

1. Runtime 不导入商品运营模块，基础依赖方向总体正确；
2. ToolDefinition、ToolRegistry、ToolExecutor、Operation、Reconciliation 和 AgentEvent 已具备通用雏形；
3. 商品运营目前只有 search_products、get_product_snapshot、compare_listing_prices、update_price 四个业务 Tool；
4. composition/product_operations.py 同时承担能力初始化、注册、PreToolUse 装配、价格策略、读工具分发、平台命令转换、应用门面与恢复辅助，职责过多；
5. ProductPreToolNormalizer 只保留 store_id、sku、target_price，无法自然支持 query、store_ids、warehouse_id、target_status 等其他工具参数；
6. StoreResourceResolver 和参数来源守卫同样围绕单店、单 SKU、改价场景；
7. _PriceBusinessPolicy 对 update_price 之外的 Tool 默认放行，新增写 Tool 时存在漏配业务策略的风险；
8. Runtime、AgentLoop 和 ToolExecutor 通过全局 adapter_key、supports_native_idempotency、supports_reconciliation 描述写执行能力；
9. _ProductReadToolHandler 通过 stable_key 的 if/elif 集中分发所有读 Tool；
10. CommerceAdapter 名称覆盖“电商平台”，实际协议只实现改价执行与回查；
11. _CommerceGateway 在两组近似的改价命令和回执之间重复转换；
12. ProductMaintenanceAgent、product-maintenance、product_maintenance 与“商品运营 Agent”的业务定位不一致；
13. Skill 第一版实现与目标设计的差异继续以 ADR-001 为准，本 ADR 不修改 Skill 源码。

ProductOperationsAgent               Agent Runtime

Runtime 与 ProductOperationsAgent 在组合根中协作，不互相包含。Runtime 负责“怎样可靠执行”，业务模块负责“执行什么、需要什么业务规则”。

## 5. 业务模块边界

### 5.1 商品查询

职责：

- 按关键字、SKU、店铺范围查询；
- 返回内部 Product 与店铺 Listing 的规范化视图；
- 不执行写操作。

建议 Tool：

- search_products
- get_listing_snapshot

### 5.2 价格运营

职责：

- 跨店价格比较；
- 单店 Listing 价格修改；
- 价格范围、币种、版本冲突等业务规则；
- 改价后的确定性回查。

建议 Tool：

- compare_listing_prices
- update_price

### 5.3 库存运营

职责：

- 查询店铺可售库存；
- 设置可售库存；
- 校验非负数量、仓库/店铺归属与版本冲突；
- 库存写入后的确定性回查。

建议 Tool：

- get_inventory_snapshot
- set_available_stock

### 5.4 商品状态

职责：

- 查询 Listing 状态；
- 上架、下架；
- 校验平台支持、目标状态转换与版本冲突；
- 状态修改后的确定性回查。

建议 Tool：

- set_listing_status

促销、广告、订单、退款、客服和售后不属于本阶段商品运营边界。

## 6. Tool 绑定模型

每个 Tool 必须显式绑定四类信息：

```python
@dataclass(frozen=True)
class ToolBinding:
    definition: ToolDefinition
    handler: ToolHandler
    pretool_registration: PreToolProfileRegistration
    execution_profile: ToolExecutionProfile | None
```

### 6.1 PreToolProfile

PreToolUse 的固定阶段顺序继续由 Runtime 管理，但每个 Tool 使用自己的业务协作对象：

```python
@dataclass(frozen=True)
class PreToolProfile:
    input_normalizer: InputNormalizer
    provenance_resolver: ArgumentProvenanceResolver
    input_requirement_resolver: InputRequirementResolver
    resource_resolver: AuthorizationResourceResolver
    business_policy: BusinessPolicy
```

Profile 中的 Session、Actor 和 ToolCall 属于本次评估上下文，不能在应用启动时提前持有。因此 ToolBinding 保存的是注册描述，实际 Profile 由工厂按调用创建：

```python
@dataclass(frozen=True)
class PreToolProfileRegistration:
    factory: PreToolProfileFactory
    policy_mode: Literal["NONE", "BUSINESS"]
    resource_mode: Literal["WORKSPACE", "RESOURCE"]
```

policy_mode 和 resource_mode 供启动期做 fail-closed 校验；factory 只负责用本次 Session、Actor 和 ToolCall 创建实际协作对象。

规则：

1. READ Tool 可以显式绑定 NoBusinessPolicy；
2. WRITE Tool 必须显式绑定具体 BusinessPolicy；
3. WRITE Tool 缺少资源解析器、权限、执行模式或业务策略时，启动期拒绝装配；
4. 未知 Tool 或漏配策略不得默认放行；
5. Pipeline 的阶段顺序统一，但参数名、资源类型和业务规则不统一。

### 6.2 ToolExecutionProfile

第一迁移阶段先把写执行元数据从 Runtime 全局配置移动到 ToolBinding：

```python
@dataclass(frozen=True)
class ToolExecutionProfile:
    adapter_key: str
    supports_native_idempotency: bool
    supports_reconciliation: bool
```

第二阶段演进为按本次调用解析：

```python
class WriteExecutionTargetResolver(Protocol):
    async def resolve_for_call(
        self,
        *,
        workspace_id: UUID,
        arguments: Mapping[str, Any],
    ) -> WriteExecutionTarget: ...

    async def resolve_by_adapter_key(
        self,
        *,
        adapter_key: str,
    ) -> WriteExecutionTarget: ...
```

resolve_for_call 用于首次执行并把 adapter_key 固定到 Operation；resolve_by_adapter_key 用于恢复与 Reconciliation，防止配置变化后改用另一个平台连接。

## 7. 平台接入边界

### 7.1 小粒度 Gateway

业务模块依赖能力接口，不依赖“万能电商 Adapter”：

```python
class PricingGateway(Protocol):
    async def get_price(self, query: PriceQuery) -> PriceSnapshot: ...
    async def update_price(self, command: UpdatePriceCommand) -> WriteReceipt: ...
    async def reconcile_price(self, command: ReconcilePriceCommand) -> ReconcileResult: ...


class InventoryGateway(Protocol):
    async def get_inventory(self, query: InventoryQuery) -> InventorySnapshot: ...
    async def set_available_stock(
        self,
        command: SetAvailableStockCommand,
    ) -> WriteReceipt: ...


class ListingGateway(Protocol):
    async def get_listing(self, query: ListingQuery) -> ListingSnapshot: ...
    async def set_status(self, command: SetListingStatusCommand) -> WriteReceipt: ...
```

一个具体平台 Adapter 可以同时实现多个 Gateway，但业务服务只依赖自己需要的接口。

### 7.2 平台绑定与路由

```text
workspace_id + store_id
        ↓
StorePlatformBinding
        ↓
platform + connection_key
        ↓
CapabilityRouter
        ↓
具体 Gateway / Adapter
```

模型不能提供 platform、connection_key、凭证引用、adapter_key 或 idempotency_key。这些字段只能由服务端根据授权资源解析。

### 7.3 平台错误归一化

Adapter 把平台私有错误映射为有限的规范错误：

- AUTH_EXPIRED
- RATE_LIMITED
- CAPABILITY_UNSUPPORTED
- NOT_FOUND
- VALIDATION_FAILED
- VERSION_CONFLICT
- PLATFORM_UNAVAILABLE
- OUTCOME_UNKNOWN

平台原始响应只能进入受控审计字段，不能直接暴露给模型。

## 8. 写操作可靠性

所有写 Tool 必须满足：

1. Operation 在外部调用前持久化；
2. operation_id 和 idempotency_key 由 Runtime 生成；
3. 外部响应丢失统一进入 UNKNOWN；
4. UNKNOWN 不盲目重试，只能由对应 ReconciliationHandler 回查；
5. Operation 固定 adapter_key 和能力标记；
6. 确认请求绑定 Tool schema 版本、规范化参数和资源版本；
7. 确认后的执行必须重新校验权限、策略和资源版本；
8. Handler 不得绕过 PreToolUse 直接取得模型自报的内部凭证或连接标识。

当前 _PriceBusinessPolicy 使用进程内字典保存确认前版本，只适合作为第一版测试接缝；目标实现必须把资源版本写入 ConfirmationRequest，并以持久化事实完成校验。

## 9. 组合根边界

composition/product_operations.py 最终只保留：

- 创建 Registry；
- 注册 Agent、Tool、Skill 可见范围和 Source；
- 构造 PreToolProfile；
- 构造 Gateway/Adapter 与 Router；
- 构造 Runtime；
- 返回 ProductOperationsApplication。

以下内容必须移出组合根：

- 价格、库存和状态业务规则；
- 读 Tool 的 if/elif 分发；
- 平台命令转换；
- Listing 查询辅助；
- 参数规范化细节；
- Reconciliation 的领域结果判断。

## 10. 命名决策

保留以下公共名词：

- Runtime
- Workspace
- Session
- Run
- AgentBackend
- ToolCall
- PreToolUse
- AgentEvent
- ToolRegistry
- ToolExecutor
- Operation
- ReconciliationService

目标命名：

| 当前名称 | 目标名称 | 迁移说明 |
|---|---|---|
| ProductMaintenanceAgent | ProductOperationsAgent | 新版本使用，旧持久化 stable_key 通过显式迁移处理 |
| product-maintenance | product-operations | 不做静默替换，发布新 AgentVersion 并迁移 Workspace 绑定 |
| ProductApplication | ProductOperationsApplication | Python 类型直接重命名 |
| get_product_snapshot | get_listing_snapshot | 发布新 ToolVersion/Tool key，旧 key 在迁移期保留兼容 |
| CommerceAdapter 协议 | PricingGateway 等 | 按业务能力拆分 |
| _ProductReadToolHandler | 独立 SearchProductsHandler 等 | 去掉集中分发 |
| _CommerceGateway | 删除或由 CapabilityRouter 取代 | 去除重复命令转换 |

AgentBackend、Run 和 AgentEvent 不改名。

Skill 最终命名不在本 ADR 决定；Skill 模型和当前实现差异以 ADR-001 为唯一事实源。

## 12. 实施阶段

### P0：纠正 Runtime 绑定边界

1. 为 Tool 建立独立 PreToolProfile；
2. 修复查询参数被价格 Normalizer 丢弃的问题；
3. WRITE Tool 策略缺失时启动失败；
4. 把 Adapter 执行元数据从 Runtime 全局字段移动到 Tool 绑定；
5. 持久化确认使用的资源版本；
6. 删除读 Tool 集中 if/elif 分发；
7. 保持既有改价行为与恢复语义不变。

### P1：重组商品运营模块

1. 统一 ProductOperations 命名；
2. 拆出 catalog、pricing、inventory、listing 模块；
3. 引入 PricingGateway、InventoryGateway、ListingGateway；
4. 增加库存查询/修改和商品上下架；
5. 为每个业务模块增加 Tool、Policy 和 Handler 契约测试。

### P2：多平台路由

1. 建立 StorePlatformBinding；
2. 引入 CapabilityRouter；
3. 写 Tool 按 store_id 解析 WriteExecutionTarget；
4. Reconciliation 按 Operation.adapter_key 找回原平台；
5. 在出现第二个真实平台需求时实现对应 Adapter。

## 13. 验收标准

目标架构完成时必须满足：

1. 新增 Tool 不修改 Runtime 主循环；
2. 新增业务模块不修改其他业务模块；
3. 新增平台只实现 Gateway、Adapter 和路由注册；
4. 不存在商品参数白名单被所有 Tool 共用；
5. 不存在新增写 Tool 默认跳过业务策略；
6. 一次 Run 可以操作属于不同平台的多个店铺；
7. Operation 能固定本次真实执行的 adapter_key；
8. UNKNOWN 可以回到原 Adapter 做确定性回查；
9. composition/product_operations.py 不包含领域策略和 Tool 分发；
10. Runtime 不导入 agents.product_operations 或 adapters.commerce；
11. 旧改价闭环、权限、确认、幂等与恢复测试继续通过；
12. 新增库存和状态工具具备同等级别的确定性测试。

## 14. 非目标与不做清单

当前不做：

- 微服务拆分；
- Kafka 或通用事件总线；
- 动态插件发现和第三方插件市场；
- 每个 Tool 一个独立服务；
- 通用 Workflow Engine；
- Multi-Agent 调度；
- 广告、订单、退款、客服和售后业务；
- 为尚未接入的平台提前实现复杂 Capability Manifest；
- 把目标设计包装成已上线的企业生产事实。
